## Bug 1 — `_to_bps` Heuristic Over-Scales UST SF and CIP Spreads

### Claimed behavior
`_to_bps(x)` in `metric_analysis.ipynb` cell 3 converts a series to basis points using threshold heuristics.

### Actual behavior
```python
def _to_bps(x: pd.Series) -> pd.Series:
    if med < 0.05:      return s * 10000.0   # decimal → bps
    if med < 20.0:      return s * 100.0     # percent → bps
    return s                                  # already bps
```

**The 20 bps threshold collides with correctly-in-bps series whose median spread happens to be < 20 bps.**

### Evidence from raw data

| Series | Raw file | Median |W| | _to_bps result | Correct action |
|--------|----------|-------------|----------------|----------------|
| Treasury_SF_2Y | treasury_sf_output.csv | **18.76 bps** | ×100 → 1,876 bps ❌ | identity |
| Treasury_SF_5Y | treasury_sf_output.csv | **17.37 bps** | ×100 → 1,737 bps ❌ | identity |
| Treasury_SF_10Y | treasury_sf_output.csv | 23.48 bps | identity ✓ | identity |
| Treasury_SF_30Y | treasury_sf_output.csv | **13.28 bps** | ×100 → 1,328 bps ❌ | identity |
| CIP_AUD_ln | cip_spreads_3m_bps.csv | **9.89 bps** | ×100 → 989 bps ❌ | identity |
| CIP_CAD_ln | cip_spreads_3m_bps.csv | **12.75 bps** | ×100 → 1,275 bps ❌ | identity |
| CIP_GBP_ln | cip_spreads_3m_bps.csv | **10.70 bps** | ×100 → 1,070 bps ❌ | identity |
| CIP_NZD_ln | cip_spreads_3m_bps.csv | **11.98 bps** | ×100 → 1,198 bps ❌ | identity |
| CIP_CHF_ln | cip_spreads_3m_bps.csv | 31.14 bps | identity ✓ | identity |
| CIP_EUR_ln | cip_spreads_3m_bps.csv | 36.23 bps | identity ✓ | identity |
| CIP_JPY_ln | cip_spreads_3m_bps.csv | 38.77 bps | identity ✓ | identity |
| arb_2 (TIPS) | tips_treasury_implied_rf_2010.parquet | 22.48 bps | identity ✓ | identity |
| arb_5 (TIPS) | tips_treasury_implied_rf_2010.parquet | **19.42 bps** | depends on stacked median | verify |

Note: `_to_bps` is applied AFTER the melt (to the full stacked column). For UST SF, the stacked
median of all 5 tenors ≈ 18 bps → multiplied by 100 → entire UST SF panel is ×100 too large.
For CIP, whether the stacked median is above or below 20 bps depends on the mix of currencies
in the melted series, but individual currencies below 20 bps will be corrupted regardless if
`_to_bps` is applied per-series.

Also: `src/slr_bucket/outcomes.py::_scale_to_bps` uses threshold `med < 5` (different from the
notebook's `med < 20`). The two code paths are inconsistent.

### Fix
Replace `_to_bps` with a deterministic `SERIES_UNITS` map. Files in `data/series/*_bps.csv`
and `*_output.csv` are already in bps. Equity `spread_*` (non-_filtered) is already in bps.
Equity `spread_*_filtered` is in percent units and needs ×100. See `fix_1_units.py`.

## Bug 2 — UST Spot–Futures Magnitude Error (~2500 bps pre-period)

### Claimed behavior
The UST spot-futures data reflects basis-point deviations between implied repo rate and OIS.

### Actual behavior
This is caused **entirely by Bug 1**: `_to_bps` multiplies the already-in-bps UST SF series by 100.
The raw `treasury_sf_output.csv` values are economically plausible:
- Treasury_SF_2Y range: [−262, +94] bps, median_abs = 18.8 bps ✓
- Treasury_SF_5Y range: [−421, +94] bps, median_abs = 17.4 bps ✓
- Treasury_SF_10Y range: [−343, +102] bps, median_abs = 23.5 bps ✓

The `sign_map["ust_spot_fut"] = -1` in CONFIG is a compensating sign flip applied because the
futures basis is negative (futures trade cheap to spot). This is mechanically fine but masks
the unit error.

### Fix
Remove `_to_bps` call in `load_ust_spot_fut()`. Use raw values directly (already in bps).
The sign_map flip is semantically defensible; retain it for the oriented spread but note that
`y_abs_bps = abs(y_bps)` makes the sign irrelevant for the regression dependent variable.

## Bug 3 — Post × TreasuryBased Collinear with Post (Single-Strategy ACTIVE Mode)

### Claimed behavior
`run_pooled_jump(..., interact_treasury=True)` in cell 12 estimates the differential Treasury
effect via `post:treasury_based` coefficient in a pooled regression.

### Actual behavior
Cell 7 defines `ACTIVE = "ust_spot_fut"` (or another single strategy), so `panel_long` contains
only one strategy. The "pooled" regression in section (B) of cell 12 runs on `subW` which is a
subset of `panel_long` — i.e., data from ONE strategy only.

When ACTIVE = "ust_spot_fut": all rows have `treasury_based = 1`
→ `post:treasury_based` = `post × 1` = `post` (perfect collinearity)
→ OLS drops one of them, or the patsy formula absorbs one into the other

When ACTIVE = "cip" or "eq_spot_fut": all rows have `treasury_based = 0`
→ `post:treasury_based` = `post × 0` = 0 (dropped as zero-variance)

**The cross-strategy identification of Treasury vs. non-Treasury effects is completely absent.**

Verification (conceptual):
```python
sub = panel_long[panel_long["strategy"] == "ust_spot_fut"]
assert (sub["treasury_based"] == 1).all()  # True → interaction ≡ post
```

### Fix
Build a proper multi-strategy panel stacking TIPS (2y,5y,10y), UST SF (2y,5y,10y), CIP (8
currencies), and equity (SPX, NDX, INDU) simultaneously. Run the pooled regression on this
17-series panel. The `post:treasury_based` coefficient is identified by comparing Treasury-based
series (6 series, treasury_based=1) against non-Treasury series (11 series, treasury_based=0).
Formula: `y_abs_bps ~ post + post:treasury_based + C(series_id) + controls`
See `fix_3_pooled.py`.

## Bug 4 — Equity Sample Size N = 14–16 (Expected ≈ 121)

### Diagnosis
The notebook runs in single-strategy mode. When generating equity tables, the notebook must
have been in an equity-active run. The equity CSV files have:
- `spread_SPX_filtered`: 3,734 non-null rows (2010–2024), median_abs = 0.436 (percent units)
- `spread_SPX`: 3,734 non-null rows (2010–2024), median_abs = 43.6 bps (already bps)

The load_equity function uses `spread_*_filtered` (0.436 range). The `_to_bps` heuristic:
- med ≈ 0.436 → NOT < 0.05 → NOT ×10000
- 0.436 < 20 → IS < 20 → ×100 → 43.6 bps ✓ (accidentally correct for equity!)

So unit conversion is NOT the equity N problem. Three likely causes:

1. **Controls sparsity**: `direct_controls` includes `issu_7_bil`, `issu_14_bil`, `issu_30_bil`.
   The treasury issuance file is at weekly/quarterly frequency with tenor_bucket pivoting needed.
   If these columns don't exist in the merged panel_long, they're dropped from the regression.
   The VIX/HY_OAS controls have full coverage (100%) in the 2019–2021 window.

2. **Event window filter in the per-strategy-bin regression**: In cell 13, the per-strategy
   binned regression drops rows with `dropna(subset=reg_cols)`. If SOFR/spr_tgcr controls are
   in `reg_cols` but have ~0.13% missing (repo file has 784 non-null out of 794 dates), this
   drops very few rows — unlikely to cause N=14.

3. **Most likely: the notebook was run for equity with `event_range=(-60,60)` and `windows=[20,60]`
   but the equity data had date coverage gaps around the specific event window, OR the `add_event_time_trading`
   function computed event_time incorrectly for the equity subsample.**

Testing add_event_time_trading on equity data:
- SPX data: 3,734 rows, 2010-01-04 to 2024-12-31
- For event_date="2020-04-01": searchsorted finds first date ≥ 2020-04-01, which is 2020-04-01
  (a Wednesday, so it's a valid trading day). Event_time=0 at that date.
- ±60 window: should give 121 rows for one series (equity has data every trading day)

**Conclusion**: N=14-16 was likely generated from a regression configuration that limited the
panel to a very narrow window, OR there is a date merging issue where the equity panel does not
align with the controls dataset. The repair pipeline will use the full multi-strategy panel
with proper controls, restoring N to the expected ≈ 121 per event window.

### Fix
Use `spread_SPX` (already in bps) instead of `spread_SPX_filtered` to eliminate unit ambiguity.
In the full pooled pipeline, the equity series will contribute ~121 obs per event × 3 indices
= ~363 obs per event window (equity). See `fix_4_equity_n.py`.

## Bug 5 — Overlapping Event Windows for 2021-03-19 and 2021-03-31

### Diagnosis
Events: ["2020-04-01", "2021-03-19", "2021-03-31"]
Calendar gap between 2021-03-19 and 2021-03-31: 12 calendar days ≈ 9 trading days

Overlap for window W (in trading days):
- W=20: pre-event of 2021-03-31 extends to 2021-03-31 − 20 t.d. ≈ 2021-03-03
         post-event of 2021-03-19 extends to 2021-03-19 + 20 t.d. ≈ 2021-04-16
         Overlap of pre/post: 2021-03-03 to 2021-03-19 → contaminated
- W=60: overlap is catastrophic (both windows cover the same ~100 day period)

### Fix
For the pair (2021-03-19, 2021-03-31):
- Drop 2021-03-19 from the per-event regression table (it is analytically dominated by the
  expiry date)
- Treat 2021-03-19 as an "announcement" event with forward-only window [0, +9] (through expiry)
- Use 2021-03-31 as the primary "exit" event with windows [±20] and [±60]
- Add overlap detection guard in the regression engine

See `fix_5_overlap.py`.

## Bug 6 — HAC Covariance Rank Deficiency

### Diagnosis
Warning text: "covariance of constraints does not have full rank. The number of constraints is
10/12, but rank is 6/7/8"

Root cause chain:
1. Equity N=14-16 (from Bug 4) with 10-12 regressors → completely underidentified
2. When `treasury_based` is constant within a single-strategy run (all 0 or all 1), the patsy
   formula `post:treasury_based + treasury_based` creates near-collinear design matrix
3. Rank deficiency from zero-variance columns (bins empty for some tenors/windows)

The `run_pooled_jump` function does NOT check the obs-to-parameter ratio before calling HAC.

### Fix
1. After fixing Bug 3 (proper multi-strategy pooling), N per regression will be ~500-2000 obs
   for the pooled spec, resolving the underidentification
2. Add guard: if N < 10 × (num_params + num_fe_levels), emit warning and skip
3. Drop zero-variance FE levels from the design matrix (already partially done in event_study.py
   lines 266-268, but not in the notebook's `run_pooled_jump`)

See `fix_6_hac.py`.
